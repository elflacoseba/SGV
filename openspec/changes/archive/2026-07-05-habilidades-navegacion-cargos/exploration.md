# Exploración — habilidades-navegacion-cargos

## Estado actual

El patrón espejo ya existe del lado **Cargo → Habilidades** y está implementado de punta a punta. En la API, `CargosController` expone el subrecurso `GET /api/v1/cargos/{cargoId}/skills` bajo el bloque `// ---- Subrecurso: habilidades del cargo ----`, devolviendo `IReadOnlyList<CargoSkillDetailDto>` mediante `ICargoSkillServicio.ListAsync(cargoId, ...)`. Ese mismo controller mantiene `PUT` y `DELETE` para la asociación puntual, lo que confirma una forma de contrato “padre + subrecurso enriquecido” ya aceptada en el repo. **Evidencia:** `src/SGV.Api/Controllers/CargosController.cs:221-295` — `"[HttpGet(\"{cargoId:guid}/skills\")]"`, `"return Ok(result);"`, `"[HttpPut(\"{cargoId:guid}/skills/{skillId:guid}\")]"`.

Ese contrato espejo está modelado con dos DTOs distintos: `CargoSkillDetailDto` para lectura GET enriquecida con `skill`, `nivel`, `skillId`, `nivelRequeridoId`, `ponderacion` y `esObligatoria`; y `CargoSkillDto` para respuestas de escritura con `skillId`, `nivelRequeridoId`, `ponderacion` y `esObligatoria`. La separación muestra un patrón claro: lectura detallada para hidratar UI y DTO más chico para comandos. **Evidencia:** `src/SGV.Aplicacion/Organizacion/Consultas/Dtos/CargoSkillDetailDto.cs:5-38` — `"GET-only detailed DTO"`, `"public Guid SkillId { get; init; }"`, `"public decimal Ponderacion { get; init; }"`; `src/SGV.Aplicacion/Organizacion/Consultas/Dtos/CargoSkillDto.cs:3-31` — `"returned by write operations"`, `"public decimal Ponderacion { get; init; } = 1.00m;"`.

En la capa web, el cliente tipado `ICargoApiClient` refleja exactamente ese subrecurso con `GetSkillsAsync`, `UpsertSkillAsync` y `DeleteSkillAsync`, y `CargoApiClient` implementa `GetSkillsAsync` contra `"{BaseRoute}/{cargoId}/skills"`, tratando `404` como colección vacía para la grilla editable. Esto es importante porque el cambio nuevo puede reutilizar el patrón “método tipado + endpoint dedicado + fallback explícito”, pero NO existe todavía el espejo `GetCargosAsync` del lado de habilidades. **Evidencia:** `src/SGV.Web/Integration/Organizacion/ICargoApiClient.cs:65-95` — `"GET /api/v1/cargos/{cargoId}/skills"`, `"Task<IReadOnlyList<CargoSkillDetailDto>> GetSkillsAsync"`; `src/SGV.Web/Integration/Organizacion/CargoApiClient.cs:138-158` — `"GetAsync($\"{BaseRoute}/{cargoId}/skills\")"`, `"if (response.StatusCode == HttpStatusCode.NotFound) { return []; }"`.

La Razor Page espejo ya publicada es `Pages/Organizacion/Cargos/Habilidades.cshtml`, con ruta `/organizacion/cargos/{id:guid}/habilidades`. Esa página es **editable**, no readonly: lista vínculos, muestra formulario de asignación, publica handlers `Asignar`, `Actualizar` y `Quitar`, y exige rol `Administrador` tanto por chequeo explícito en handlers como por ocultamiento de acciones en la vista. **Evidencia:** `src/SGV.Web/Pages/Organizacion/Cargos/Habilidades.cshtml:1-3` — `"@page \"/organizacion/cargos/{id:guid}/habilidades\""`; `src/SGV.Web/Pages/Organizacion/Cargos/Habilidades.cshtml:102-161` — `"asp-page-handler=\"Actualizar\""`, `"formaction=\"?handler=Quitar...\""`; `src/SGV.Web/Pages/Organizacion/Cargos/Habilidades.cshtml.cs:122-127`, `157-162`, `244-252`, `342-347` — `"if (!EsAdministrador) { return Forbid(); }"`.

El entry point de ese espejo ya fue agregado en el listado de cargos: la columna **Acciones** de `Cargos/Index` incorpora un botón azul con ícono `ti ti-stars` hacia `/Organizacion/Cargos/Habilidades`, visible solo cuando `!Model.IsDeletedView`. También se agregó un botón textual en `Cargos/Details`. Eso confirma el patrón de descubribilidad del lado Cargo, pero también deja claro que el nuevo cambio NO parte de cero: debe replicar solo la mitad inversa, no rediseñar el módulo. **Evidencia:** `src/SGV.Web/Pages/Organizacion/Cargos/Index.cshtml:160-168` — `"href=\"@Url.Page(\"/Organizacion/Cargos/Habilidades\", new { id = item.Id })\""`, `"data-bs-title=\"Habilidades\""`; `src/SGV.Web/Pages/Organizacion/Cargos/Details.cshtml:69-78` — `"<i class=\"ti ti-stars me-1\"></i>Habilidades"`.

Del lado **Habilidad → Cargos**, hoy NO existe ese espejo. `SkillsController` solo expone catálogo maestro (`GET /api/v1/skills`, `GET /api/v1/skills/{id}`, `GET /api/v1/skills/consulta`) y mutaciones del catálogo (`POST`, `PUT`, `DELETE`, `PATCH /reactivar`); no hay ningún subrecurso tipo `/api/v1/skills/{skillId}/cargos`. **Evidencia:** `src/SGV.Api/Controllers/SkillsController.cs:15-108` — rutas `"api/v1/skills"`, `"{id:guid}"`, `"consulta"`; `src/SGV.Api/Controllers/SkillsController.cs:119-239` — solo create/update/delete/reactivate; ausencia en todo el archivo de una ruta `"{id:guid}/cargos"`.

La ausencia también se confirma en la aplicación y la integración web. `IHabilidadApiClient` termina en `ReactivarAsync` y no declara ningún método para listar cargos asociados a una habilidad, mientras que `HabilidadApiClient` tampoco implementa nada equivalente. La búsqueda de `QueryActiveCargosBySkillId`, `CargosBySkill` o métodos homólogos no devolvió implementaciones en `src/SGV.Api`, `src/SGV.Aplicacion` ni `src/SGV.Infraestructura`; solo aparecieron artefactos del espejo cargo→skills ya conocido. **Evidencia:** `src/SGV.Web/Integration/Habilidades/IHabilidadApiClient.cs:47-57` — `"Task<PagedResult<HabilidadDto>> QueryAsync"`, `"Task<HabilidadCommandResult> ReactivarAsync"`; `src/SGV.Web/Integration/Habilidades/HabilidadApiClient.cs:122-147` — `QueryAsync` y `ReactivarAsync` como últimos métodos; búsqueda repo: sin coincidencias para `QueryActiveCargosBySkillId` y sin endpoint `skills/{id}/cargos`.

La página de listado de habilidades confirma el gap visual pedido por producto. En `Habilidades/Index.cshtml`, la vista activa solo muestra `Detalle`, `Editar` y `Eliminar`; no hay botón `Cargos`. Además, la visibilidad está segmentada por `!Model.IsDeletedView`, igual que en Cargos, por lo que el lugar natural para sumar el nuevo botón es ese mismo bloque de acciones de filas activas. **Evidencia:** `src/SGV.Web/Pages/Organizacion/Habilidades/Index.cshtml:156-176` — `"Detalle"`, `"Editar"`, `"Eliminar"`; ausencia de cualquier enlace a `/organizacion/habilidades/{id}/cargos`; `src/SGV.Web/Pages/Organizacion/Habilidades/Index.cshtml.cs:60-64` — `"public bool IsDeletedView"`.

`Habilidades/Details` hoy es readonly y preserva el retorno al listado mediante `ReturnStatus`, pero NO expone navegación hacia cargos asociados. Esto importa porque el espejo de Cargos sí terminó tocando `Details`; sin embargo, en este cambio el producto dejó bloqueado que el botón de entrada viva solo en las filas activas del `Index` de Habilidades. La inspección del detalle sirve entonces para documentar una diferencia de alcance respecto del espejo previo, no para inferir una tarea nueva. **Evidencia:** `src/SGV.Web/Pages/Organizacion/Habilidades/Details.cshtml:67-78` — solo `Editar` y `Volver al listado`; `src/SGV.Web/Pages/Organizacion/Habilidades/Details.cshtml.cs:41-61` — `ReturnStatus` y `ReturnToListUrl`.

También conviene marcar una restricción estructural del dominio: la relación `CargoHabilidad` ya existe como entidad de unión con `CargoId`, `HabilidadId`, `NivelRequeridoId`, `Ponderacion` y `EsObligatoria`, y en infraestructura tiene índice único compuesto `{ CargoId, HabilidadId }`. Eso significa que para el espejo skill→cargos no hace falta inventar otra fuente de verdad ni otra tabla: el trabajo es puramente de lectura/proyección y navegación. **Evidencia:** `src/SGV.Dominio/Habilidades/CargoHabilidad.cs:12-40` — constructor con `cargoId`, `habilidadId`, `nivelRequeridoId`, `ponderacion`, `esObligatoria`; `src/SGV.Infraestructura/Persistencia/Configuraciones/CargoHabilidadConfiguracion.cs:11-34` — `"HasIndex(e => new { e.CargoId, e.HabilidadId }).IsUnique();"`.

## Capacidades OpenSpec impactadas

La capacidad claramente impactada es `habilidad-web-listado-detalle-baja`, porque el listado activo hoy define que una fila muestra `Detalle`, `Editar` y `Eliminar`, y además declara explícitamente como fuera de alcance las asignaciones `habilidad↔cargo`. El nuevo cambio rompe deliberadamente esa frontera, aunque solo desde navegación de lectura en web. Por eso esa spec no alcanza con un ajuste cosmético: hay que actualizarla o partirla para reflejar que el catálogo maestro ahora sí expone un entry point hacia relaciones con cargos. **Evidencia:** `openspec/specs/habilidad-web-listado-detalle-baja/spec.md:25-65` — requirement de acciones por segmento; `openspec/specs/habilidad-web-listado-detalle-baja/spec.md:92-97` — `"No incluye asignaciones habilidad↔cargo"`.

La capacidad `habilidad-management` también queda impactada en API, porque hoy define que `/api/v1/skills` cubre solo catálogo maestro y que las asignaciones a cargos o personas quedan fuera de esa porción. Si el espejo se implementa con un subrecurso `GET /api/v1/skills/{id}/cargos`, esa spec deberá modificarse o complementarse con una capability nueva hermana, del mismo modo que `cargo-skill-query-contract` especializó la lectura del lado Cargo. **Evidencia:** `openspec/specs/habilidad-management/spec.md:5-6` — `"Las asignaciones a cargos o personas quedan fuera"`; `openspec/specs/habilidad-management/spec.md:143-152` — `"MUST NOT encontrar operaciones de CargoHabilidad"`.

El espejo previo sugiere además una tercera capacidad específica, análoga a `cargo-skill-query-contract`. Esa spec actual documenta el contrato enriquecido de `GET /api/v1/cargos/{cargoId}/skills`, incluidos ids, flags y objetos anidados, y explícitamente protege que el payload padre no se contamine. El nuevo cambio probablemente necesite un sibling equivalente para `GET /api/v1/skills/{skillId}/cargos`, porque hoy no hay una spec canónica que describa cómo debería verse “un cargo asociado a una habilidad” desde la API. **Evidencia:** `openspec/specs/cargo-skill-query-contract/spec.md:5-18`, `37-57` — contrato enriquecido del subrecurso y aislamiento del payload padre.

No veo evidencia de que `cargo-skill-ui-tabla-editable` deba cambiar en este slice. La nueva página pedida es readonly desde la perspectiva de Habilidad, y los botones por fila solo navegan a `Cargo/Details` y a la página ya existente `Cargos/Habilidades`; no cambian la tabla editable en sí misma. **Evidencia:** `src/SGV.Web/Pages/Organizacion/Cargos/Habilidades.cshtml:77-167` — la grilla editable ya existe y cubre el flujo write; el pedido actual solo agrega navegación desde Habilidades.

## Asunciones y restricciones del repositorio aplicables

La solución sigue una Clean Architecture estricta: dominio, aplicación e infraestructura quedan debajo de API y `SGV.Web` actúa como shell/composition layer con clientes HTTP tipados. Para este cambio eso implica que la nueva navegación web NO debería saltarse la API ni leer EF Core directo desde Razor Pages. **Evidencia:** `openspec/config.yaml:3-10` — `"Architecture: Clean Architecture"`; `src/SGV.Web/Integration/Habilidades/HabilidadApiClient.cs:13-20` y `src/SGV.Web/Integration/Organizacion/CargoApiClient.cs:11-17` — patrón de cliente tipado HTTP vigente.

La persistencia usa MySQL 8 + Pomelo y las reglas de unicidad sobre registros activos se resuelven con columnas generadas cuando hay soft delete. Para `CargoHabilidad`, sin embargo, la relación hoy está modelada con índice único compuesto directo `{ CargoId, HabilidadId }` y un check de `Ponderacion > 0`, sin soft delete propio en la unión. Por eso el cambio explorado no necesita migración ni ajustes de unicidad si se mantiene como lectura/navegación. **Evidencia:** `docs/decisiones-implementacion.md:7-14` — proveedor MySQL/Pomelo y estrategia de unicidad con soft delete; `src/SGV.Infraestructura/Persistencia/Configuraciones/CargoHabilidadConfiguracion.cs:11-34` — check constraint e índice único compuesto; `src/SGV.Infraestructura/Persistencia/Entidades/CargoHabilidadEntity.cs:6-23` — la entidad no tiene `IsDeleted`.

La segmentación `status=activas|eliminadas` es una convención del repo tanto en API como en web para listados de catálogo. Del lado Habilidades ya está implementada en `GET /api/v1/skills/consulta`, en `Habilidades/IndexModel` y en el markup del toggle Activas/Eliminadas. Si la nueva página lista cargos asociados, debería respetar esa semántica en el nuevo query/read model en lugar de mezclar activos y eliminados. **Evidencia:** `src/SGV.Api/Controllers/SkillsController.cs:68-108` — `status` cae a `activas` o `eliminadas`; `src/SGV.Web/Pages/Organizacion/Habilidades/Index.cshtml.cs:96-114`, `240-246` — normalización de segmento y `BuildToggleSegmentoRouteValues`; `src/SGV.Web/Pages/Organizacion/Habilidades/Index.cshtml:59-62` — toggle visible en la UI.

Las operaciones de escritura del catálogo `SkillsController` requieren rol `Administrador`, mientras que las lecturas admiten cualquier usuario autenticado. En paralelo, la página `Cargos/Habilidades` también hace `Forbid()` si el usuario no es admin. Eso crea una restricción importante: la nueva página puede ser readonly para cualquier autenticado, pero uno de los botones de fila definidos por producto navega a una pantalla write-only para administradores. **Evidencia:** `src/SGV.Api/Controllers/SkillsController.cs:119-126`, `170-177`, `200-227` — `[Authorize(Roles = RolesSgv.Administrador)]` en mutaciones; `src/SGV.Web/Pages/Organizacion/Cargos/Habilidades.cshtml.cs:122-127`, `157-162`, `244-252`, `342-347` — guard clause admin por handler.

El repositorio ya tiene `strict_tdd: true` como regla OpenSpec y cobertura previa para el espejo cargo→skills tanto en API como en web. Eso sugiere que el cambio nuevo debería espejar estrategia de pruebas antes que inventar otra: test del subrecurso API y tests de Razor Page/listado web. **Evidencia:** `openspec/config.yaml:11-18`, `43-48` — `strict_tdd: true`; `tests/SGV.Tests/Api/CargoSkillControllerTests.cs:87-207` — cobertura del GET subrecurso cargo→skills; `tests/SGV.Tests/Web/Cargo/CargoIndexPageTests.cs:117-174` y `tests/SGV.Tests/Web/Cargo/CargoDetailsPageTests.cs:113-171` — cobertura de entry points web del espejo previo.

## Mapeo del trabajo a hacer

El primer bloque es API/aplicación/infraestructura de lectura, porque hoy no existe ninguna consulta skill→cargos. El espejo más directo sería un subrecurso en `SkillsController`, análogo a `CargosController.GetSkills`, apoyado por un DTO de lectura específico y por una proyección desde `CargoHabilidad`. La evidencia actual muestra que el repo ya separa DTO de lectura enriquecida y cliente tipado por subrecurso, así que el trabajo real empieza por definir ese contrato simétrico, no por tocar Razor primero. **Evidencia:** `src/SGV.Api/Controllers/CargosController.cs:223-239`; `src/SGV.Aplicacion/Organizacion/Consultas/Dtos/CargoSkillDetailDto.cs:14-38`; `src/SGV.Infraestructura/Persistencia/Repositorios/CargoSkillRepository.cs:35-68`.

El segundo bloque es integración web del lado Habilidades. `IHabilidadApiClient` y `HabilidadApiClient` hoy solo conocen el catálogo maestro; para alimentar una nueva página `Habilidad → Cargos` van a necesitar un método nuevo, del mismo modo que `ICargoApiClient.GetSkillsAsync` alimenta `Cargos/Habilidades`. No hay patrón read-only equivalente ya implementado del lado Habilidad, así que la costura natural es agregarlo ahí, no reutilizar `ICargoApiClient` desde una página de Habilidades. **Evidencia:** `src/SGV.Web/Integration/Habilidades/IHabilidadApiClient.cs:12-57`; `src/SGV.Web/Integration/Organizacion/ICargoApiClient.cs:65-95`.

El tercer bloque es la nueva Razor Page readonly. La ruta candidata no existe todavía dentro del folder `Pages/Organizacion/Habilidades`: hoy solo hay `crear`, `editar` y `detalles`, mientras que el espejo del lado Cargos usa la forma `/organizacion/cargos/{id}/habilidades`. Eso deja libre un patrón simétrico tipo `/organizacion/habilidades/{id}/cargos`, con PageModel propio y navegación de retorno consistente con el módulo de Habilidades. **Evidencia:** `src/SGV.Web/Pages/Organizacion/Habilidades/Details.cshtml:1`, `Create.cshtml:1`, `Edit.cshtml:1` según búsqueda de rutas; `src/SGV.Web/Pages/Organizacion/Cargos/Habilidades.cshtml:1` como patrón espejo ya vigente.

El cuarto bloque es el entry point en `Habilidades/Index`. Producto ya fijó que el botón `Cargos` vaya solo en filas activas, así que el lugar correcto es el mismo bloque donde hoy viven `Detalle`, `Editar` y `Eliminar`. El PageModel ya tiene helpers `BuildEditRouteValues`, `BuildDetailsRouteValues` y `BuildToggleSegmentoRouteValues`, lo cual permite agregar una ruta preservando convenciones de contexto si más adelante hiciera falta. **Evidencia:** `src/SGV.Web/Pages/Organizacion/Habilidades/Index.cshtml:156-176`; `src/SGV.Web/Pages/Organizacion/Habilidades/Index.cshtml.cs:222-246`.

El quinto bloque son los CTAs internos de la nueva página: por decisión de producto, cada fila debe navegar a `Cargo/Details` y también a la página existente `Cargos/Habilidades` que gestiona las habilidades de ese cargo. El primer enlace reutiliza una superficie readonly ya existente; el segundo salta a una superficie write-only. Técnicamente ambos destinos ya están implementados, así que la página nueva no necesita resolver edición inline, pero sí va a depender de contratos mínimos que incluyan al menos `Cargo.Id`, `Codigo`, `Nombre` y, para segmentación, probablemente estado activo/eliminado. **Evidencia:** `src/SGV.Web/Pages/Organizacion/Cargos/Details.cshtml:31-80`; `src/SGV.Web/Pages/Organizacion/Cargos/Habilidades.cshtml:1-235`.

El sexto bloque es testing. El espejo previo ya dejó una estrategia muy clara: API con tests dedicados del controller del subrecurso y web con tests de listado/entry point más tests específicos de la página objetivo. El lado Habilidad ya cuenta con `HabilidadIndexPageTests` y `HabilidadDetailsPageTests`, por lo que el cambio nuevo puede extender ese patrón sin inventar harness nuevo. **Evidencia:** `tests/SGV.Tests/Api/CargoSkillControllerTests.cs:87-207`; `tests/SGV.Tests/Web/Habilidad/HabilidadIndexPageTests.cs:44-76`; `tests/SGV.Tests/Web/Habilidad/HabilidadDetailsPageTests.cs:35-56`.

Por último, verifiqué que no existe un change activo o archivado llamado `pagina-cargos-por-habilidad` ni una variante coincidente en `openspec/changes`. Eso reduce el riesgo de sobrescribir artefactos, pero deja abierta la necesidad de alinear naming para no recrear accidentalmente un slug muy parecido al pedido histórico. **Evidencia:** búsqueda `openspec/changes/**/*pagina*cargos*habilidad*` sin coincidencias.

## Riesgos y áreas de incertidumbre

El riesgo más fuerte no es técnico sino de frontera funcional: la página nueva es readonly por alcance, pero uno de sus botones navega a `Cargos/Habilidades`, que hoy hace `Forbid()` para usuarios sin rol `Administrador`. Si la nueva página queda disponible para cualquier autenticado —como hoy ocurre con `SkillsController` en lectura y con `Habilidades/Index`— entonces un usuario no admin podría ver un botón que desemboca en `403`. Eso no invalida el cambio, pero SÍ es una contradicción observable que proposal/spec van a tener que fijar explícitamente. **Evidencia:** `src/SGV.Api/Controllers/SkillsController.cs:15-18`, `68-108`; `src/SGV.Web/Pages/Organizacion/Cargos/Habilidades.cshtml.cs:122-127`, `157-162`, `244-252`, `342-347`.

El segundo riesgo es de modelado OpenSpec: las specs actuales de `habilidad-web-listado-detalle-baja` y `habilidad-management` excluyen asignaciones `habilidad↔cargo`. Si el cambio se documenta solo como “agregar un botón” pero no actualiza esa frontera, quedará una inconsistencia documental seria entre comportamiento y capability declarada. **Evidencia:** `openspec/specs/habilidad-web-listado-detalle-baja/spec.md:92-97`; `openspec/specs/habilidad-management/spec.md:143-152`.

El tercer riesgo es de naming y shape contractual. El espejo cargo→skills usa DTOs con ids del vínculo y objetos anidados; del lado skill→cargos todavía no existe un nombre canónico equivalente ni una proyección establecida. Si se intenta “reciclar” `CargoDto` sin un DTO específico, podría faltar contexto para las acciones de la página o contaminar contratos padre. **Evidencia:** `src/SGV.Aplicacion/Organizacion/Consultas/Dtos/CargoSkillDetailDto.cs:5-38`; `openspec/specs/cargo-skill-query-contract/spec.md:37-46`.

El cuarto riesgo es de alcance respecto del espejo previo. El change `cargos-navegacion-habilidades` terminó tocando `Index`, `Details`, la página editable y varios tests web. En este nuevo slice, el producto ya dejó bloqueado que el botón de entrada viva solo en `Habilidades/Index`, no en `Habilidades/Details`. Si esa diferencia no se deja explícita desde propuesta en adelante, es fácil caer en scope creep “por simetría” y tocar más superficies de las necesarias. **Evidencia:** `src/SGV.Web/Pages/Organizacion/Habilidades/Index.cshtml:156-176`; `src/SGV.Web/Pages/Organizacion/Habilidades/Details.cshtml:67-78`; `openspec/changes/cargos-navegacion-habilidades/exploration.md:90-117`.

El quinto riesgo es de naming de change. No apareció una carpeta `pagina-cargos-por-habilidad`, pero el antecedente verbal existe y el slug nuevo propuesto es `habilidades-navegacion-cargos`. Si en fases siguientes se mezclan ambos nombres, pueden duplicarse artefactos o perder trazabilidad histórica. **Evidencia:** búsqueda `openspec/changes/**/*pagina*cargos*habilidad*` sin coincidencias; artefactos canónicos del espejo previo en `openspec/changes/cargos-navegacion-habilidades/*`.
